# ER Dose RAW 파싱·적재 파이프라인 및 RAW/EUV 재적재 판단 개선

> 이 문서는 Pull Request 본문 전용으로 작성한다.

## 작업 배경

ER Dose RAW 대용량 처리 과정에서 조회, 파싱, 적재가 순차적으로 실행되어 각 단계의 대기 시간이 누적되고 있었다.

또한 원천에 동일 이벤트가 중복으로 존재하면 source와 parsed의 전체 건수가 달라져, 실제 누락이 없어도 불필요한 전체 재적재가 발생할 수 있었다.

## 주요 변경 사항

### 1. RAW 파싱·적재 파이프라인 역할 분리

- 메인 스레드는 청크 조회, 파싱, 설비별 상태 갱신을 담당한다.
- 적재 worker 1개는 이전 청크의 `COPY` 적재를 담당한다.
- 이전 청크를 적재하는 동안 다음 청크를 조회·파싱하도록 처리 단계를 겹쳤다.
- 대기 중인 적재 작업은 최대 1개로 제한해 처리 순서와 메모리 사용량을 유지한다.
- 적재 `Future`의 예외는 메인 배치로 전달한다.
- 모든 적재가 완료된 후 일별 서머리 테이블을 갱신한다.
- Repository는 동기식 DB 적재를 담당하고, Processor가 파이프라인 흐름을 제어하도록 책임을 정리했다.

### 2. RAW/EUV 재적재 판단 개선

- source와 target의 전체 건수를 먼저 `COUNT(*)`로 비교한다.
- 전체 건수가 같으면 해당 날짜를 스킵한다.
- target 건수가 0이면 `DISTINCT` 조회 없이 즉시 전체 재적재한다.
- 전체 건수가 다르고 target 데이터가 있으면 기존 `fetch_source_count()`를 `distinct=True`로 다시 호출한다.
- `(eq_name, code, code_occur_time)` 기준 중복 제거 건수가 target 건수와 같으면 원천 중복으로 판단해 재적재를 스킵한다.
- 중복 제거 후에도 건수가 다르면 기존과 같이 대상 파티션을 `TRUNCATE`하고 전체 재적재한다.
- 해당 판단 로직은 `CountReloadProcessor`에서 RAW/EUV 공통으로 처리한다.

## 성능 결과

약 1,973만 건, `chunk_size=30000` 조건에서 운영 실행 시간을 비교했다.

| 구분 | 실행 시간 | 처리량 |
| --- | ---: | ---: |
| 적용 전 | 4,175초 | 약 4,727 rows/s |
| 적용 후 | 2,896초 | 약 6,815 rows/s |
| 개선 결과 | 1,279초 단축 | 약 1.44배 |

전체 실행 시간은 약 30.6% 감소했다.

## 검증

- RAW/EUV 전체 건수 일치 시 재적재하지 않는지 확인
- target 건수가 0일 때 `DISTINCT` 없이 재적재하는지 확인
- 원천 중복만 존재할 때 재적재하지 않는지 확인
- 실제 건수 차이가 있을 때 `TRUNCATE` 후 재적재하는지 확인
- 적재 worker 예외가 메인 배치로 전달되는지 확인
- 관련 테스트 71개 통과

## 리뷰 포인트

- 적재 worker를 1개로 제한해 DB 적재 순서와 메모리 사용량을 유지하는지 확인
- `DISTINCT` 쿼리가 전체 건수가 다른 경우에만 실행되는지 확인
- RAW/EUV의 재적재 판단이 공통 processor에서 동일하게 적용되는지 확인
